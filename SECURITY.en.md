# Security

## Reporting a vulnerability

If you find a security problem, **don't open a public issue**. Use GitHub's private reporting: the **Security → Report a vulnerability** tab of this repository. Include the steps to reproduce it and which versions of Nanuq and Jellyfin you use.

## Verifying the official APK

Official APKs are signed with a single certificate (`CN=Nanuq, O=Nanuq`, RSA). SHA-256 fingerprint:

```
9A:B9:59:A9:62:BD:DF:AA:1E:D3:0F:3B:2D:94:8D:55:F8:CB:54:41:B4:74:02:30:1E:EB:E7:9D:5A:74:D3:BD
```

Check it with `apksigner verify --print-certs nanuq-<version>-release.apk`: the “certificate SHA-256 digest” must match. An APK with a different signature isn't official, even if it says it's Nanuq. The private key is never in this repository.

## What Nanuq protects

Nanuq is a client: it stores the Jellyfin session (the token) on the device and talks to the server you choose. The protections aim to ensure that neither a malicious server, nor tampered metadata (for example, tags of songs downloaded from the internet), nor someone on your network can run code in the app, steal the session or use the app against your server or your network.

- **Everything that comes from outside is escaped** before being shown (titles, artists, lyrics, playlist names, SomeDL and LrcLib responses, other devices).
- **Outside JSON with no tricks:** when reading responses from Jellyfin, SomeDL, the party (both ways), your other devices, network discovery and Discord, the keys `toString`, `valueOf` and `__proto__` are discarded. An object like `{"toString": 1}` makes any conversion to text fail: a server could stop the lists containing that song from loading and, in the **party, any device on the local network could close the computer's app with a single message, without knowing the code** (versions 1.31.0 to 1.44.0; fixed in 1.44.1). Also, on the computer, a message from a phone that causes any error only cuts that connection, and texts and ids are converted safely (`ptStr`, `str`).
- **Server ids are cleaned** (`sid()`: only letters, numbers and dashes) before being used in API routes or in HTML, and numeric fields are converted to numbers. An id like `../Users/…` can't divert a request, which carries your token, to another part of the API.
- **Strict Content-Security-Policy for scripts** (`script-src 'self'`): only the code in the app's files runs (`i18n.js`, `app.js`). Nothing inline: no injected `<script>`, no attributes like `onerror=`, no `javascript:` links, no `eval`. So even if some malicious text got in as HTML, it couldn't run code. Inline or third-party stylesheets (except Google Fonts), iframes, plugins, `<base>` and submitting forms to another page aren't accepted either.
- **Narrow native bridges**: the CORS-free requests on Android (`NanuqAndroid.http`) and Linux (`nanuq:http`) only accept the SomeDL API routes (`/add`, `/status`, `/get-queue`, `/get-version`) and don't follow redirects. On Linux, the main process also only answers the app's own page.
- **Narrow Android downloads**: they only download addresses shaped like Jellyfin's (`…/Audio/{id}/universal` and `…/Items/{id}/Images/Primary`), with no user in the URL and following redirects only within the same server. What's downloaded goes back to the page through the local server, so this prevents using downloads to read other services on your network.
- **Lyrics you type or paste**: before saving them on the device or uploading them to Jellyfin, control characters, text-direction characters and HTML tags are removed, with a maximum of 200,000 characters and 5,000 lines; the `.lrc` file is built with no line breaks or timestamps slipped into the song details, and the file name is cleaned. When shown, they're always escaped.
- **Electron fuses** (Linux and Windows): the executable can't be used as a Node interpreter (`ELECTRON_RUN_AS_NODE`), doesn't accept code through `NODE_OPTIONS` or a debugger through `--inspect`, only loads its own package (`app.asar`) and, on Windows, validates that package's fingerprint at startup; `file://` without extra privileges and encrypted cookies.
- **Electron (Linux and Windows)**: `contextIsolation`, `sandbox`, no `nodeIntegration`; only the notifications, full-screen and clipboard-write permissions are granted (no microphone, camera or location); external links open in the browser.
- **Integrity of what's stored on disk:** nothing Nanuq stores in your data folder is run or played without being checked. Personal data (and, on Android, the downloads index) uses AES-256-GCM, which detects any change; party songs too, block by block. In the desktop app the code always comes from the installed package (read-only in RPM and Flatpak) and, before the page opens, whatever Chromium could run from a previous session is deleted: the service worker with its copy of the app (no longer registered outside the browser) and the compiled-code cache; the HTTP cache is off. Preferences (theme, volume, sort orders) are checked when read: an altered value goes back to the default. On Android everything lives in the app's private storage, which other apps can't read or change; also, an Opus download or prefetched song is only kept if all its Ogg pages arrive complete with a correct CRC (conversions don't send a size, so otherwise a cut-off download was kept as good), and the audio type the server reports is only accepted in the `audio/…` form.
- **Android**: the WebView has no file access; if the page tried to navigate outside the app, only `http(s)` links open (in the browser): no `intent:`, `file:`, `content:` or `javascript:`; the session and downloads don't travel in backups or when moving data to another phone (`allowBackup="false"` and `dataExtractionRules`).
- **Party (watch party, only while you open it on the computer):** it's the only thing listening on your local network: TCP 47864 (a home-made WebSocket, no dependencies) and UDP 47865 (so phones can find the room). Both close when the party or the app closes.
  - **Only your local network:** although it listens on every interface (so phones can find it), it only answers private addresses (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10, `::1`, `fc00::/7`, `fe80::/10`). A public IPv6 or Yggdrasil (`200::/7`, a global network) can't get in even if the firewall allows it. UDP discovery only answers your network and at most 30 times per second.
  - Joining requires the **6-digit code** shown on the computer's screen (compared in constant time). After 5 errors from the same address it's blocked for a minute; if 30 errors pile up (from any address: with IPv6 it's easy to change addresses), the code changes on its own and for a minute nobody can try codes (those already in come back with their key). You can ask for another code any time; those already in keep their key (valid only while the room lasts; if a phone sleeps or loses the network, its place —and its key— is kept for up to 2 h; “Leave” cancels it immediately). Guests can't remove songs from the list (only cancel theirs while it arrives): that, skipping and reordering are only done by the computer.
  - Before joining, only a small message (≤ 4 KB) is accepted and there are 10 s to send it; at most 4 connections without introducing themselves per address and 64 HTTP connections in total (nobody can fill the room with silent connections). At most 12 guests and 24 connections; messages ≤ 1 MB, text ≤ 450 KB; unmasked frames, frames with extensions or with fake lengths close the connection (tested with a frame announcing 500 MB).
  - Songs arrive in a private folder **on disk** (permissions 0700/0600; on Linux, `~/.cache/nanuq/nanuq-fiesta-*`, in the Flatpak inside `~/.var/app/com.nanuq.app/cache`; not in RAM) and are stored **encrypted and authenticated** (AES-256-GCM, in 64 KB blocks, with a random key that only exists in the room's memory): another app of your user can't read or change them; if a single byte of the file changes (or it's cut short, or blocks are swapped), it's detected on playback, nothing altered is served and the song is removed from the list. Limits: 80 MB per song, 800 MB in total, 60 in the list and 10 per guest. They're only accepted if their first bytes are audio (MP3, FLAC, Ogg, WAV, M4A, WebM, AAC); otherwise they're deleted. They're served to Nanuq's window only through `127.0.0.1`, with a random room token and a fixed type (`nosniff`). The cover the phone sends (a thumbnail, ≤ 150 KB) is only accepted if its bytes really are JPEG, PNG or WebP (no SVG or anything else); it lives in memory while the song is in the list and is served the same way, through `127.0.0.1` with the token. The room's phones see it in their list by asking the party port (`GET /fiesta/c/<id>?k=<key>`): only with a guest key from that room; without a key or with a fake one, nothing.
  - **They delete themselves:** when they finish playing, when removed, if they've been in the list for more than 2 h or stopped arriving halfway (3 min), when the room closes and when Nanuq opens (leftovers from a room that didn't close properly).
  - What each phone sends (names, titles, lyrics) is treated as untrusted: it's limited, cleaned and always shown as text. The phone also treats what the computer sends as untrusted.
  - The phone downloads the song from **its own** Jellyfin with its own session: the computer never receives the guest's token or server address.
  - The themes each phone sends are only used if they exist in Nanuq (a name like `constructor` pointed to a function inherited from JavaScript and broke the igloo: fixed in 1.40.1). A sleeping phone keeps its place for at most 2 h, and stops trying to rejoin after 2 h without contact with the room (or after about 30 s of failed attempts with the app on screen). When the room or the app closes, the computer immediately cuts all the phones' connections, including half-open ones.
  - It travels unencrypted inside your local network (like Jellyfin over `http://`): use it on a trusted network.
- **Local servers** only on `127.0.0.1`: on Android, routes with a random 128-bit token and read-only access to downloads and ahead-of-time songs, with 10 s in total and at most 100 headers to send each request (before, another app on the phone could tie up every thread by sending endless headers; fixed in 1.44.1); on Linux and Windows, only the app's files, only GET/HEAD, only if the request is addressed to `127.0.0.1` or `localhost` (against “DNS rebinding” from an internet page) and without crashing on malformed paths (before, a null byte in the path —which any page open in your browser could request— closed the app).
- **What's next in the queue, saved ahead of time (Android):** it's downloaded with the same rules as downloads (only Jellyfin audio addresses, redirects only to the same server), to the app's private cache folder; it's deleted when the app opens and when the song leaves the window. Limits: 40 songs, 400 MB per song, 1 GB in total and always 300 MB free.
- **Logging out** revokes the token in Jellyfin.
- **Your data saved on the device is encrypted.** Session (token), queue, play counts for downloads, DJ session, songs requested from SomeDL, recent servers, saved lyrics, your library's index to build the albums, the lyrics index to search by lyrics and the device id:
  - **Linux and Windows:** a file encrypted with AES-256-GCM; its random key is stored encrypted with the system keyring (GNOME Keyring or KWallet on Linux, DPAPI on Windows, through `safeStorage`). Responses whose URLs carry the token aren't stored in the disk cache, and older versions' cache is cleared once.
  - **Android:** AES-256-GCM with a key from the Android Keystore, which can't be taken out of the phone. The downloads index (what you downloaded, how much you play it) is also encrypted. Everything lives in the app's private storage, which Android also isolates and encrypts, and it doesn't travel in backups.
  - What earlier versions stored in plain text is migrated automatically when the app opens.
  - If the keyring can't be opened, Nanuq **writes nothing in plain text**: it warns you and asks you to log in again. If the system has no keyring, data is stored as before and **Settings → Data saved on this device** says so.
  - Interface preferences (theme, volume, sort orders, language) aren't encrypted: they say nothing about you.
  - **Browser:** there's no secure store a web page can reach; the browser stores them in your profile.
- **Your year with Nanuq:** the data comes from your server, only from your user: from the Playback Reporting plugin (if your user is an administrator) or from Jellyfin's basic data. Nanuq only **reads** the plugin: it queries by day with your cleaned user id, the date it builds itself and the fixed filter `Audio` (the plugin puts the filter as is into its SQL), and it doesn't use its free SQL query. Nanuq no longer keeps its own history (the one from earlier versions is deleted). The video is drawn on a `<canvas>` (titles and artists are drawn text, never HTML); covers are requested with `fetch` without credentials, only images up to 8 MB, reduced before being used. Recording stops at 59 s or 200 MB. On Android, the video reaches the system in validated chunks (only MP4/WebM, at most 300 MB, file name set by the app) and “Share” only accepts the video Nanuq just saved (not any file in the gallery); on Linux only downloads generated by the app itself are allowed.
  - What the server answers for the recaps is treated as untrusted: cleaned ids, bounded durations (0 to 6 h; it counts if it lasted 30 s or more), invalid hours ignored, at most 3,000 plays per day and 200,000 in total, and queries stop if you leave the screen.
  - **Exported videos aren't encrypted**: they're yours to share (they contain your artists and songs). They're saved where you choose or in *Movies › Nanuq*.
- **Memory and resources:** Nanuq is written in JavaScript and Java (memory-safe) and includes no native code of its own. Everything that comes from outside has limits so a malicious server or network can't exhaust memory or close the app: SomeDL responses (4 MB), Android notification covers (8 MB and decoded already reduced, against pixel “bombs”), downloaded songs (1 GB and free space), downloaded covers (15 MB), servers found on the network (32), paginated lists (20,000 artists, 5,000 favorites), another device's queue (3,000), view cache (400), lyrics (200,000 characters). Android's local server handles at most 32 connections and doesn't crash on malformed requests. Audio and image decoding happens in Chromium's/WebView's sandboxed process; keep Nanuq and Android's WebView up to date.
- **Unencrypted password warning** when logging in over `http://` to an internet address.

## Known limits

- **`http://` is allowed** because Jellyfin is usually on the local network without HTTPS. Over the internet, use HTTPS or a VPN (Nanuq warns you).
- The CSP allows `style="…"` attributes (`style-src-attr 'unsafe-inline'`): the interface uses them for calculated colors and positions. They don't run code. Inline scripts are **not** allowed.
- **Streaming carries the token in the URL** (`api_key`), as Jellyfin requires so the browser's player can request the audio: it shows up in your server's or proxy's logs.
- **Network server discovery** (UDP 7359) shows whatever anyone on your network answers: check the address before typing your password.
- **My devices** (remote control between your Nanuqs):
  - There's no direct connection between devices: everything goes through your Jellyfin, with your session. Only sessions of **your same user** with the Nanuq client show up as “your devices”. A session claiming to be “Nanuq” isn't enough: to show up it needs your username and password (or your token). A session of another user claiming to be Nanuq doesn't show up or trigger automatic connections.
  - “Same network” is decided by the address **the server sees** (not the one the device declares). If Jellyfin is behind a proxy without “Known proxies” configured, everyone appears with the proxy's address; this only affects the automatic connection between your own devices.
  - The list shows each device's address, so you can recognize one that isn't yours. If you see an unknown one, change your password and close its sessions in Jellyfin (Dashboard → Devices).
  - **Commands this Nanuq accepts:** those that play songs (`Play`) and repeat/shuffle (`GeneralCommand`) are only accepted if they come from **your user**. Jellyfin itself sets who sends them, so it can't be faked. To accept another user's, you have to turn it on in Settings (“Accept commands from other users”, off by default). Pause, next, previous and seek (`Playstate`) don't carry a trustworthy sender: there the limit is set by Jellyfin, which only delivers them if they come from your user or from someone with the **“Allow remote control of other users”** permission (administrators, by default). Check in Dashboard → Users who has that permission.
  - Nanuq doesn't announce commands it doesn't use (like showing messages).
  - **DJ across devices:** the DJ session's state (rounds, what already played and, when sending the music, to which device) is stored in your Jellyfin as a display preference of **your user** (`/DisplayPreferences`, client “Nanuq”); only your own Nanuqs read it. When read, it's treated as untrusted: cleaned ids, bounded texts (names ≤ 80, introductions ≤ 400 characters), only known round types and always shown as text.
- **Discord (optional, off by default):** if you turn on “Show what you're listening to on Discord”, Nanuq sends the Discord app on your computer the title, artist, album and time of what's playing; Discord shows it on your profile to whoever can see it. With “With the cover” (only if your Jellyfin is on the internet over https), the cover's address —and with it your server's— also goes to Discord. Nanuq doesn't query third-party services for covers. Only the app's page can ask the main process for it, and texts are cleaned and bounded. Nanuq only connects to a `discord-ipc-N` socket **owned by you** (in `/tmp` another user of the computer could create a fake one to see what you listen to) and reads what it answers with limits (messages ≤ 64 KB, buffer ≤ 1 MB); tested against a malicious Discord (negative or huge lengths, broken JSON, bursts, garbage, objects with `toString`) without crashing or growing in memory. On Flatpak it has read-only permission for the `discord-ipc-0` socket and access to the run folders of Discord, Vesktop and Equibop on Flatpak (`$XDG_RUNTIME_DIR/.flatpak/<id>/xdg-run`, where those apps create their socket). That access is “create” (`:create`), not read-only: those folders only exist after opening that app once in the session and Flatpak doesn't share what doesn't exist when Nanuq opens, so with read-only access Nanuq didn't see Discord if it opened later (since 1.40.2). With that, Nanuq can create those empty folders and write to them (it doesn't), but it doesn't see the rest of your files.
- The Inter and Outfit fonts are loaded from Google Fonts.
- The Windows installer isn't signed (code signing requires a paid certificate): Windows warns about it when opening it. Network server discovery (UDP) may make Windows Firewall ask the first time.
- On Linux, the system controls' cover arrives at 150 px because that's how Chromium delivers it; improving it would require a new dependency to publish the controls over D-Bus, and it was decided not to add it.
- While the app is open, your data is in memory unencrypted (it needs it to work). Encryption protects what's stored on disk.
- A malicious program already running as your user on the computer (outside a sandbox like Flatpak) can do much more than touch Nanuq's data: change an AppImage or the Windows install (both in folders you own), or get into the process while it's open. What Nanuq guarantees is that what it stores on disk isn't used if it was altered; against that, the protection is the system's (Flatpak, read-only RPM, antivirus).
- `npm audit` flags a slowness issue in `minimatch` inside electron-builder, the tool that builds the Linux packages: it isn't included in the installed app.
